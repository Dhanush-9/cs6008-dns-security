# Phase 2 Report: On-Path Response Forgery (Cache Poisoning)

## 1. Overview of Results

In Phase 2, an adversary container (`attacker` at `172.16.2.100`) was positioned on the resolver subnet (`172.16.2.0/24`). A diversion route installed on `core-router` directed all inbound DNS traffic destined for `resolver` (`172.16.2.10`) through the attacker. 

The attacker executes a custom C++ packet interceptor using `libpcap` to inspect, relay, and selectively forge DNS responses.

## 2. Experimental Observations & Evidence

### 2.1 What the Resolver Cached
After clearing the resolver cache via `rndc flush` and querying `example.com.` from `client`, the resolver's internal database was dumped using `rndc dumpdb -cache`.

From `phase2/evidence/attack-cache-dump.log`:
```text
;
; Start view _default
;
; Cache dump of view '_default' (cache _default)
;
example.com.		599	NS	domain-ns.example.com.
; authanswer
			599	A	172.16.1.30
; glue
domain-ns.example.com.	599	A	172.16.3.30
; authanswer
www.example.com.	599	A	172.16.1.20
```
**Observation**: The resolver accepted and cached the forged record `example.com. A 172.16.1.30` as an authoritative answer (`authanswer`) with a TTL of 600 seconds. Meanwhile, `www.example.com` remains cached with its genuine IP `172.16.1.20`.

## 3. Analysis & Theoretical Questions

### 3.1 Why does the attack succeed? (Properties of Plain DNS)
Plain DNS operates over stateless UDP with **no built-in cryptographic authentication or integrity verification**. A recursive resolver determines whether a response is valid solely by verifying that the incoming packet matches four metadata fields from its outstanding query:
1. **Transaction ID (TXID)**: A 16-bit identifier generated by the resolver.
2. **UDP Port 4-Tuple**: Source IP must match the nameserver queried, destination IP must match the resolver, source port must be 53, and destination port must match the ephemeral port the resolver used.
3. **Question Section**: The Question Name (QNAME), Query Type (QTYPE), and Query Class (QCLASS) must match the query.
4. **Bailiwick Authority**: The responding server must be recognized as having authority over the domain name being answered (e.g. `domain-ns` at `172.16.3.30` is authoritative for `example.com`).

Because plain DNS lacks digital signatures (such as DNSSEC), any packet that reproduces these header values correctly is accepted as truth by the resolver.

### 3.2 What advantage does the on-path position give over an off-path attacker?
An **off-path adversary** (such as Kaminsky-style blind spoofing from the external internet):
- Cannot observe queries traversing the resolver network.
- Must guess the 16-bit TXID ($2^{16} = 65,536$ possibilities) AND the resolver's randomized ephemeral UDP source port (~$64,000$ possibilities), giving a search space of $\approx 4.2 \times 10^9$ combinations.
- Must win a race condition against the legitimate authoritative server's response. If the legitimate response arrives first, the cache is filled and further spoofed packets are rejected.

In contrast, our **on-path adversary**:
- **Zero Guessing**: Sits directly on the diverted network path and inspects the genuine packet in real time. It reads the exact TXID (`0xc2dc`) and destination UDP port directly from the packet headers.
- **No Race Condition**: Because traffic is diverted through the attacker by routing, the attacker receives the genuine reply from `domain-ns` **before** the resolver does. The attacker simply **drops/suppresses the legitimate reply** and injects the forged answer. The resolver never sees the real response.

### 3.3 How does the interceptor leave non-target names untouched?
The interceptor achieves transparent pass-through for non-target traffic via three gating mechanisms implemented in `interceptor.cpp`:

1. **Selective Content Gating**:
   ```cpp
   bool is_target = (config.forge_mode &&
                     qname == config.target_domain &&
                     qtype == 1 &&
                     ancount > 0 &&
                     std::string(src_ip_str) == config.domain_ns_ip);
   ```
   - If `qname != "example.com"` (e.g., `www.example.com`), `is_target` is `false`.
   - If `qtype != 1` (e.g., IPv6 `AAAA` queries), `is_target` is `false`.
   - If the packet is a referral (`ancount == 0` from `root-ns` or `tld-ns`), `is_target` is `false`.
   - If the source IP is not `172.16.3.30` (`domain-ns`), `is_target` is `false`.

2. **Transparent Layer-2 Relaying**:
   Whenever `is_target` is `false`, the packet falls through to `relay_packet()`. The interceptor rewrites the Ethernet destination MAC to the resolver's MAC (`3e:6c:75:3f:0d:ca`), sets the source MAC to the attacker, recomputes the IP and UDP checksums, and injects the frame back onto `eth0` via `pcap_inject()`.

3. **Bailiwick Compliance**:
   By allowing root and TLD referrals to pass through untouched and only forging the authoritative reply from `172.16.3.30`, the resolver's iterative state machine operates normally without tripping bailiwick violations or dropping intermediate delegations.
